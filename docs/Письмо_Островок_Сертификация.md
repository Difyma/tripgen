## Краткое резюме

Благодарим за обратную связь! Ниже ответы на вопросы по сертификации:

### 1. Почему показываются тестовые отели (test_hotel)

**Причина:** В текущей development-конфигурации включен fallback на тестовые отели:

```env
ETG_ENABLE_TEST_FALLBACK=true
```

Когда API возвращает ошибку или пустой результат, система автоматически показывает demo-данные. Это сделано для разработки, чтобы не блокировать работу при проблемах с API.

**Решение:** При переходе на боевой режим мы установим:
```env
ETG_ENABLE_TEST_FALLBACK=false
CERT_MODE=real
```

Все запросы будут идти напрямую к ETG API, тестовые отели останутся только для ручного тестирования.

### 2. Почему реферальные ссылки некорректны

**Причина:** В dev-режиме при ошибке API используется fallback, и все ссылки мапятся на `test_hotel`.

**Решение:** После отключения fallback ссылки будут генерироваться корректно:
- Реальные hotel_slug из API
- Правильные даты из поиска (DD.MM.YYYY-DD.MM.YYYY)
- Корректное количество гостей

### 3. Почему не отображается информация об отелях (налоги, отмена)

**Причина:** При fallback на demo-отели эти данные не загружаются из реального API. Код для отображения есть, но данные приходят из статических fixture.

**Решение:** После перехода на боевой API вся информация будет отображаться:
- Налоги и сборы
- Политика отмены с дедлайнами
- Время заезда/выезда
- Типы питания

### 4. IP-адреса

Адрес **95.165.80.49** — не актуален. Мы используем serverless-архитектуру (Vercel/AWS) с динамическими IP.

**Просим:** Использовать аутентификацию по ключу (Key ID + API Token) без привязки к IP.

### 5. Статическая информация (Content API)

Готовы перейти на статический подход с Content API:
- **Объем:** ТОП-500 отелей для начала
- **Частота:** Еженедельное обновление
- **Сроки:** 2 недели после согласования доступа
